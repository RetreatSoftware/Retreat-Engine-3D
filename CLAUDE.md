# Retreat-Engine-3D

The 3D game engine of the Retreat ecosystem: rendering, game loop, networking, and other fundamental runtime systems. It integrates gameplay modules from `Retreat-Modules` and is the base that `Retreat-Forge` assembles into playable games.

This file contains project facts and rules only. Personal preferences belong in `CLAUDE.local.md`.

The root `../CLAUDE.md` also applies here. This file may narrow its scope (see "Status") but not relax its rules; its verification and infrastructure rules apply only once this repository has code that needs them.

## Status

Early stage: the Engine Sandbox is being built (first window, then commands, snapshots, models, materials, shaders, physics, UI, browser bridge). Do not implement anything beyond what is explicitly requested.

## Ecosystem context

Sibling repositories (cloned next to this one under `Retreat/`):

- `Retreat-CoreSDK` — shared math, data structures, utilities, common abstractions. Has no Retreat dependencies.
- `Retreat-Modules` — independent gameplay crates (inventory, combat, loot, ...).
- `Retreat-Forge` — builder UI: selects modules, resolves dependencies, builds the game, AI customization.
- `Retreat-Website` — web platform: catalog, accounts, rankings, marketplace.

Vision documents live in the `Retreat` repository: [FRAMEWORK.md](https://github.com/RetreatSoftware/Retreat/blob/main/FRAMEWORK.md) (engine/Forge) and [PLATFORM.md](https://github.com/RetreatSoftware/Retreat/blob/main/PLATFORM.md) (platform). Read `FRAMEWORK.md` before making architectural decisions.

## Decided technical direction

- **Language:** Rust. Performance is a hard requirement.
- **Rendering:** `wgpu`. Treat WebGL2 limits as the baseline; WebGPU-only features must be feature-gated.
- **Targets:** native (also used for the authoritative game server) and WebAssembly (`wasm32-unknown-unknown`) for the browser. Games run in the player's browser with no download.
- **Build:** Cargo workspace. Both native and WASM targets must build in CI from the start.
- **Module composition:** compile-time. Each gameplay module is an independent crate with a manifest (capabilities, dependencies, compatibility, configuration) declared in its `Cargo.toml` metadata. Forge resolves and validates; Cargo only compiles. Do not use Cargo features as the plugin mechanism.
- **No dynamic plugin loading, no custom scripting language** for now. Keep game logic data-driven and behind contract traits so a scripting layer stays possible later.
- **Authority:** the server owns game state. Games never mint currency or change balances; economic operations go through the platform adapter to trusted backend services.
- **Engine base: Bevy 0.20.** Do not write a custom ECS, renderer or asset system; extend Bevy instead.
- **Bevy is a direct dependency, pinned once per workspace.** The version lives in `[workspace.dependencies]` of the root `Cargo.toml`; crates declare `bevy.workspace = true`. Do not reach Bevy only through a re-export: Bevy's derive macros (`#[derive(Component)]`, ...) look for `bevy` in the using crate's own `Cargo.toml` and fail with "cannot find `bevy_ecs`" otherwise. Other repositories (Modules) pin the same version in their own workspace.
- **Contract crate `retreat_engine_api`**: the only engine crate modules may depend on. Holds the command layer (`CommandRegistry`, `run_command_line`, `CommandArgs`, `CommandError`, `AppCommandExt::register_command`), `SimulationRng`, the physics body description (`PhysicsBody`, `PhysicsBodyKind`, `PhysicsShape`) input mapping (`InputAction`, `InputActions`, `InputKey`, `AppInputExt`, `InputActionSystems`, `HELD_ONLY`) the camera description (`GameCamera`) sound playback (`SoundPlayback`, `SoundKind`) animation playback (`AnimationPlayback`, `ClipPlayback`) saving (`SaveStore`, `SaveBackend`, `SaveError`, `SavedData`, re-exported `serde_json`) and the UI toolkit (`UiPanel`, `UiButtonEntry`, `UiPanels`, `AppUiExt`, `compute_panel_layout`).
- **Commands.** Ids are one word, `area.verb` (`assert.position`, later `physics.spawn_box`). A handler is `fn(&mut World, &CommandArgs) -> CommandResult`; it validates its arguments with `CommandArgs::expect_count` / `parse` so every error names the command, the bad value and the usage. Registering an id twice panics. Every entry point (scripts, UI, keys, browser bridge) calls `run_command_line`; never call feature logic directly from UI or input code.
- **Command scripts** (`--commands <file>`, `.cmds`): one command per line, `#` comments and blank lines cost no frame. When a script is loaded, time runs on `TimeUpdateStrategy::FixedTimesteps(1)` (exactly one fixed tick per app update, chosen over `ManualDuration` because it cannot drift from the fixed timestep) and the runner runs in `FixedUpdate`, one line per tick. Bevy's first update starts the clock and runs no tick. The first failing line logs `file:line: message` and exits with code 1. Without a script, time is real (interactive play).
- **Snapshots** (`snapshot <name>` → `target/snapshots/<name>.png`, relative to the working directory). Names are letters, digits, `_`, `-` only. The command starts the GPU capture and registers it in `PendingCommandWork`; the script holds until the PNG is written (or fails after `PENDING_WORK_TIMEOUT`, 30 s of wall-clock time: pending work runs in real time, and a tick lasts 3 ms on a GPU but 250 ms on a software renderer, so a tick-based timeout was too short on one and too long on the other). Any future command whose work finishes on a later frame uses `PendingCommandWork` the same way. Under a script, shaders compile synchronously (`RenderPlugin::synchronous_pipeline_compilation`), so a snapshot never catches a half-compiled scene.
- **Headless** (`--headless`): `DefaultPlugins` without `WinitPlugin`, `ScheduleRunnerPlugin::run_loop(0)`, no primary window, `ExitCondition::DontExit`. Cameras that target the primary window are redirected to one offscreen image (`HEADLESS_RESOLUTION` 1280x720, same as the default window) and marked `ShadowLodOrigin` (keeps Bevy's windowed shadow-LOD choice). Each headless frame waits for the GPU (`RenderDevice::poll`), because without a window nothing paces frames and a slow software GPU would fall minutes behind. Game code never checks headless; it spawns cameras as usual. Measured: windowed and headless PNGs are byte-identical on the same GPU, and repeat runs are byte-identical.
- **Software renderer** (`--software-renderer`): `WgpuSettings::force_fallback_adapter` (WARP on Windows, lavapipe on Linux). Used by CI. Pixels differ slightly from a hardware GPU, so compare PNGs only within one adapter; cross-platform determinism is checked with `state.hash`.
- **Models** (`model.spawn <name> <path> <x> <y> <z> <scale>`): loads glTF scene 0 as a `WorldAssetRoot` (Bevy 0.20 renamed `SceneRoot`/`Scene`/`SceneInstanceReady` to `WorldAssetRoot`/`WorldAsset`/`WorldInstanceReady`). Paths are relative to the app's `assets` folder (`sandbox/assets/` under `cargo run`, which sets `CARGO_MANIFEST_DIR`; running the `.exe` directly looks next to the exe). `..` is rejected; absolute paths are native-only and load through `load_builder().override_unapproved()`, because the engine sets `AssetPlugin::unapproved_path_mode = Deny`. The load is `PendingCommandWork`: finished on `WorldInstanceReady`, failed when `recursive_dependency_load_state` is `Failed`. The path rule is shared with textures: `asset_paths.rs` (`resolve_asset_location`, `load_asset`).
- **Materials** (`material.set_color <name> <r> <g> <b>`, sRGB 0–1; `material.set_texture <name> <path>`, PNG only, base color reset to white). Both act on the named entity **and its descendants** with a `StandardMaterial`, so `fox` recolors a whole model. **Copy on write:** each target gets its own edited copy of its material; shared materials (all instances of one glTF) are never edited in place. `set_texture` holds the script until the image loads.
- **Hot reload** (native only): the sandbox enables Bevy's `file_watcher` feature for non-wasm targets. Bevy 0.20 reloads a changed image but existing materials keep drawing the old GPU copy, even when marked changed; `refresh_materials_using_reloaded_images` gives each entity using a reloaded image a fresh copy of its material (new asset id). Checked by `scripts/verify/hot_reload_texture.sh` (swaps a file during the run, uses `texture.wait_for_reload`; fails without the fix). Revisit when Bevy refreshes materials itself.
- **Shader materials** (`shader.apply <name> <material>`): an app registers each custom `Material` type once under a short name with `AppShaderMaterialExt::register_shader_material::<M>(name, make)` (adds Bevy's `MaterialPlugin::<M>` and an entry in `ShaderMaterialRegistry`). `shader.apply` gives the named entity and every `Mesh3d` below it one new instance of that material, removing its previous material component (standard or another registered one: a mesh with two material components is drawn twice), and holds the script until the shader file loads. The shader path is read from `Material::fragment_shader`, which must return a file path. The sandbox registers `stripes` (`sandbox/src/stripes_material.rs`, `sandbox/assets/shaders/stripes.wesl`), animated by `globals.time`.
- **Shader files are `.wesl`** (WGSL plus `import`). Bevy 0.20 moved its own shaders to WESL and passes a plain `.wgsl` file to the GPU unprocessed: no imports, no `constants::MATERIAL_BIND_GROUP`. A `.wesl` file imports Bevy's modules (`import bevy_pbr::render::forward_io::VertexOutput;`) and binds material data at `@group(constants::MATERIAL_BIND_GROUP)`. WebGL2 baseline: uniform buffers only (no storage buffers, no `#[bindless]`).
- **A GPU pipeline that fails to compile fails the script** (`gpu_pipeline_errors.rs`): a render-world system scans `PipelineCache` for pipelines that failed for good (`ProcessShaderError`, `CreateShaderModule`; `ShaderNotLoaded` / `ShaderImportNotYetAvailable` are skipped because Bevy retries them, and slow lavapipe hits them on every run) and passes the messages (with their causes) to the main world, which fails the running script against its last line. Without it Bevy only logs the error and the mesh disappears, so a check would pass. Pipelines compile a frame or two after the line that caused them, so the reported line may be one after the real cause.
- **Entity names are unique and namespaced.** Commands find entities by `Name` (`entity_names.rs`), and a lookup that finds two fails. Commands that create named entities call `ensure_name_is_free`. glTF nodes inside a model are renamed `<model>/<node>` (`namespaced_node_name`, e.g. `fox/b_Head_05`), because glTF files name nodes freely (Fox.glb has a node named `fox`).
- **Third-party assets** live under `sandbox/assets/` and each one is listed with its license in `sandbox/assets/CREDITS.md`. Prefer small CC0 files; CC-BY needs the credit line. `models/Fox.glb` (163 KB, Khronos sample, CC0 model + CC-BY 4.0 rig/conversion).
- **Pending work costs no tick.** While a script holds on `PendingCommandWork`, the `Last`-schedule system `hold_time_while_script_waits` pauses `Time<Virtual>`: updates keep loading assets and rendering, but no fixed tick runs and simulation time (physics, `globals.time` in shaders) does not advance. So the N-th line runs on the same tick and at the same simulation time on every machine, however long loading or capturing takes. The wall-clock timeout is checked there too. Closed the earlier gap where ticks kept running during a hold (needed once the animated shader made pictures depend on time).
- **Platform layer** (`crates/retreat_engine/src/platform/`): `mod.rs`, `native.rs`, `wasm.rs` are the only files with `cfg(target_arch = "wasm32")`. Both sides provide the same items: `HAS_FILE_SYSTEM`, `SCRIPT_END_EXITS_APP` (native: `quit` and a failed script exit the process so the code reaches CI; browser: the page stays up so `__retreat.status()` can be read), `launch`, `primary_window` (browser: canvas `#retreat-canvas`, fit to parent), `asset_meta_check` (browser: `Never`, no `.meta` 404s), `store_snapshot` (native: file; browser: memory) and `PlatformPlugin` (browser: the bridge systems).
- **One entry point for apps:** `retreat_engine::launch(window_title, add_game_plugins)`. Native reads process arguments and the `--commands` file; the browser reads the page URL (`?commands=<path>&seed=<n>`, parsed by the pure `LaunchOptions::from_url_query_pairs`) and fetches the script over HTTP before building the app, so a browser run starts from exactly the state a native run does (required for `state.hash` equality). `quit` sets `QuitRequested`; the runner ends the script.
- **Browser bridge** (`platform/wasm.rs`, exposed by `web/index.html` as `window.__retreat`): `command(line)` (Promise; resolves `"ok"` once the command and its pending work finished, rejects with the error; refused while a launch script runs), `status()` (JSON from the pure `script_status_json`: `loading`, `starting`, `none`, `running` + line, `passed`, `failed` + failure), `snapshot(name)` (runs `snapshot <name>`, returns a PNG data URL), `snapshotPng(name)`, `snapshotNames()`. Requests are queued by JavaScript and served by a Bevy system, one per frame, so a command never runs inside a system. Snapshots are PNG-encoded in Rust (`image` crate) on both platforms.
- **Browser build and checks:** `scripts/web/build.sh` builds with the `web-dev` profile (dev without debug info), runs `wasm-bindgen --target web --remove-name-section` (about 82 MB instead of 150) and fills `target/web/` (page, assets, `scripts/verify`). `wasm-bindgen-cli` must match the `wasm-bindgen` version in `Cargo.lock` (installed with `cargo install wasm-bindgen-cli --version <x> --locked`; chosen over trunk, which downloads binaries at build time). `node scripts/web/run_in_browser.mjs <script.cmds>` (Node 22+, no npm packages) serves `target/web`, runs the script in headless Chrome/Edge with SwiftShader WebGL2 through the DevTools protocol, saves snapshots to `target/snapshots/web/` and exits 0/1. Measured: every `scripts/verify` script passes in the browser, and `physics_boxes` / `toolbar` give the native hashes (Windows, Linux and WASM agree). CI's `browser` job runs them all. A hidden browser pane gets no animation frames, so drive the browser through `run_in_browser.mjs`, not a background tab.
- **Randomness:** everything that changes game state draws from the `SimulationRng` resource, seeded by `--seed` (default `DEFAULT_SEED` = 0). Never create another RNG for simulation.
- **Cross-repository dependencies are git dependencies** on the public GitHub repositories (`retreat_rng = { git = "https://github.com/RetreatSoftware/Retreat-CoreSDK" }` in `[workspace.dependencies]`). `Cargo.lock` pins the commit; `cargo update -p retreat_rng` picks up a new CoreSDK commit. Revisit when crates need versions (private registry or crates.io).
- **Engine/module split** (FRAMEWORK.md §12): this repository holds **capabilities** (rendering, input mapping, audio playback, animation playback, storage, UI toolkit, physics simulation, networking); gameplay that decides how a game uses them (camera controllers, character controllers, which sound or clip plays, menus, what gets saved) is a module in Retreat-Modules. A capability belongs here when it needs platform-specific code, a determinism or authority guarantee, or the same behaviour in every game. Every capability a module needs gets a library-neutral entry in `retreat_engine_api` (as `PhysicsBody` did); do not add gameplay to the engine because it is convenient.
- **Modules are Bevy plugins** (`impl Plugin`) with a manifest in `[package.metadata.retreat]`, in the `Retreat-Modules` repository (one workspace, one crate per module; see its CLAUDE.md). The sandbox adds `retreat_module_spawner` (`spawner.rain <count>`, checked by `scripts/verify/module_spawner.cmds`; its `rain` input action on key R is checked by `module_spawner_input.cmds`) and `retreat_module_orbit_camera` (`orbit.start <camera> <radius> <height>`, `orbit.stop`, `orbit.set_angle`; held arrow keys rotate a `GameCamera` at 90 degrees per second of fixed time; checked by `scripts/verify/module_orbit_camera.cmds`) and `retreat_module_sfx` (`sfx.play <path>`, `sfx.music <path>|off`, key P plays `sounds/beep.wav`; checked by `scripts/verify/module_sfx.cmds`) and `retreat_module_fox_walk` (`fox.set_speed <model> <speed>` blends Survey/Walk/Run; checked by `scripts/verify/module_fox_walk.cmds`) and `retreat_module_highscore` (`score.add|reset|save|load|show`; saves a versioned document and migrates version 1; checked by `scripts/verify/module_highscore.cmds`) and `retreat_module_menu` (`menu.toggle`, Escape toggles a centered pause menu panel; checked by `scripts/verify/module_menu.cmds`) as a git dependency pinned by `Cargo.lock`. Modules depend on `retreat_engine_api` through git; the root `Cargo.toml` `[patch."https://github.com/RetreatSoftware/Retreat-Engine-3D"]` redirects that to the local `crates/retreat_engine_api`, so modules and engine share one `CommandRegistry` type (two copies of the crate would be two different types). After changing the contract crate: push it, then `cargo update -p retreat_engine_api` in Retreat-Modules.
- **Input mapping** (`retreat_engine_api/src/input_actions.rs`, `retreat_engine/src/input_actions.rs`): a module declares actions with `AppInputExt::register_action(InputAction { id, command_line, default_keys })`. Keys are the contract enum `InputKey` (letters, Space, Enter, Escape, Tab, arrows, ShiftLeft, ControlLeft, MouseLeft/Right/Middle); `INPUT_KEY_NAMES` is the one name table (parsing, messages) and `to_bevy_input` the one mapping onto Bevy `KeyCode`/`MouseButton` (exhaustive `match`). **One-shot:** `dispatch_pressed_actions` (`Update`) runs an action's command line through `dispatch_command_line` when a bound key is `just_pressed`; two actions on one key both run, in id order, once per frame each. **Held:** `InputActions::is_held`, recomputed in `FixedUpdate` in `InputActionSystems` (after `CommandScriptSystems`) from `pressed`, never `just_pressed`; module systems that read it order `.after(InputActionSystems)` so native (multi-threaded) and WASM (single-threaded) agree. Commands: `input.key_down|key_up|tap <key>` (scripts write the same `ButtonInput` a keyboard does, so scripted presses test the bindings; `tap` is down for exactly one tick), `input.bind|unbind <action> <key>`, `input.list`, `assert.input_held|input_not_held <action>`. Startup check (`Plugin::finish`): an action whose command is not registered panics naming both; duplicate action ids panic. A held-only action (continuous input, no command) declares `command_line: HELD_ONLY` (an empty string, named so it is greppable). Limits: no axis/analog input, no gamepad, no text input, a key `just_pressed` is read in `Update` so real-time presses are per frame. Checked by `scripts/verify/input_actions.cmds` (asserts `state.hash` equal on Windows and in the browser).
- **Cameras** (`retreat_engine_api/src/game_camera.rs`, `retreat_engine/src/camera.rs`): a camera is an entity with a unique `Name` and a library-neutral `GameCamera { position, target, up, fov_degrees }`. It `#[require(Camera3d, Transform)]`, so the real camera exists the moment it is spawned (the headless offscreen redirect finds it as before); `sync_game_cameras` (`Update`, `Changed<GameCamera>`) is the one place that maps it onto `Transform` (look-at) and `Projection` (perspective, fov in radians). Modules move a camera only by editing `GameCamera`, never `Transform`/`Projection`. `GameCamera::validate` (pure, tested) rejects non-finite values, fov outside 1-179 degrees, position equal to target and `up` parallel to the view; commands validate a copy before storing it, and a direct invalid edit fails the running script. Commands: `camera.set_position|look_at <name> <x> <y> <z>`, `camera.set_fov <name> <degrees>`. No controller in the engine: orbit/follow/first-person cameras are modules (`retreat_module_orbit_camera`). The sandbox camera is a `GameCamera` (`sandbox_camera`); its pictures are byte-identical to before. Limits: one perspective projection (no orthographic yet), no camera switching or multiple viewports. Checked by `scripts/verify/camera.cmds`.
- **Audio** (`retreat_engine_api/src/sound_playback.rs`, `retreat_engine/src/audio.rs`; library: Bevy's own `bevy_audio`, decided with the user; the alternative `bevy_kira_audio` was rejected as a new dependency that would lock us in more): a sound is an entity with a unique `Name` and a library-neutral `SoundPlayback { path, volume (0-2), looping, kind: Effect|Music }`. `start_sound_playback` maps it onto Bevy's `AudioPlayer` + `PlaybackSettings` (the one mapping). **Whether a sound is "playing" is logical, never read from the sound card:** the entity exists until a one-shot's file length (read from the decoder) has passed on the fixed clock `Time<Fixed>` from the frame it was added (`sound_has_ended`, pure and tested), or until `audio.stop`; loops play until stopped; starting `Music` despawns the previous music. So scripts assert `assert.audio_playing|audio_not_playing <name>` and `assert.audio_volume <name> <v>` with the same result on a machine with no speakers, in CI and in the browser. Commands: `audio.play <name> <path> <volume> <once|loop>` (holds the script until the file loads, like `model.spawn`), `audio.music <name> <path> <volume>`, `audio.stop <name>`, `audio.stop_all`, `audio.volume <name> <v>`, `audio.status`. Paths follow `asset_paths.rs` (`.wav` and `.ogg`; `.wav` needs Bevy's `wav` feature, enabled in `retreat_engine/Cargo.toml`, which adds the `hound` crate). **Browser:** audio contexts start suspended until a user gesture; `web/index.html` wraps `AudioContext` before the engine starts, remembers each context and resumes them on the first `pointerdown`/`keydown`/`touchend`; `platform::AUDIO_NEEDS_USER_GESTURE` (true in the browser) tells `audio.status` to say so, `__retreat.audioState()` lists the states, and `run_in_browser.mjs` prints them before and after a real key press (verified: `["suspended"]` then `["running"]`). A machine without an audio device logs a warning and plays nothing; scripts still pass. Limit: a sound started by a module (not by `audio.play`) learns its length only once the file has loaded, so its logical end can be later than start + length on a slow load (assert only "playing" soon after and "not playing" long after). No spatial audio, mixing buses, fades or pitch yet. Test sounds are generated tones (`scripts/assets/make_test_sounds.mjs`, CC0, credited in `sandbox/assets/CREDITS.md`). Checked by `scripts/verify/audio.cmds` (hash `0x8e09235baaf959dc` in the browser too: sound changes no simulation state).
- **Animation** (`retreat_engine_api/src/animation_playback.rs`, `retreat_engine/src/animation.rs`; library: Bevy's own `bevy_animation`, no new dependency): a model (the entity `model.spawn` makes; it now keeps `ModelGltf`, the handle of the whole glTF file) plays what its library-neutral `AnimationPlayback { clips: [ClipPlayback { clip, weight 0-1, speed 0-4, looping }] }` lists: one clip, or several with weights as a blend; an empty list holds the pose. `ensure_rig` (called by commands and by `build_animation_rigs` every `Update`) builds an `AnimationRig` once the file and scene are loaded: one `AnimationGraph` node per clip name (sorted, so never hash order) on the scene's `AnimationPlayer`. **Time is the engine's:** each clip's time lives in the rig; `advance_clip_times` (`FixedUpdate`, ordered `.after(CommandScriptSystems)`) adds `fixed tick * speed`; `apply_animation_poses` (`Update`) writes the pose into Bevy's `ActiveAnimation` with **speed 0**, so Bevy's real-time advance never moves it (`clip_pose_time`: loops wrap, one-shots hold just before the end). Fixed time pauses while a script waits, so pose = f(tick): repeat runs are byte-identical and the browser draws the same pose. Interactive play adds the clock's `overstep` for smoothness (zero under scripts). A clip's time starts when it joins the list and survives weight changes (so a speed-driven blend never restarts); finished one-shots leave the list and keep their pose; a clip the file lacks fails the script naming the file's clips. Commands: `animation.list|stop <model>`, `animation.play <model> <clip> <once|loop> <speed>`, `animation.blend <model> <clipA> <clipB> <weightB>`, `assert.animation_playing <model> <clip>`, `assert.animation_time <model> <clip> <seconds>`, `assert.animation_weight <model> <clip> <w>`. Poses are render-only: `state.hash` is unchanged. Limits: no cross-fade transitions, masks or events; one `AnimationPlayer` per model; Fox.glb clips are `Survey` (3.417 s), `Walk` (0.708 s), `Run` (1.158 s). Checked by `scripts/verify/animation.cmds` (repeat run PNGs byte-identical; same pose in the browser).
- **Saving** (`retreat_engine_api/src/save_store.rs`, `retreat_engine/src/storage.rs`, backends in `platform/`; JSON through `serde_json`, chosen with the user: already in `Cargo.lock` through Bevy, readable saves; the no-dependency string format was rejected as fragile for modules): each module owns **one JSON document** saved under its module id (letters, digits, `_`, `-` only: it is a file name and a storage key). **Format:** `{ "format": 1, "module": "<id>", "version": <n>, "data": {...} }`. `format` is `SAVE_FORMAT_VERSION`: a newer one is refused (`SaveError::FormatTooNew`); `module` must equal the id it was loaded under; `version` is the module's own data version, chosen by the module, which migrates older data itself (`SavedData::check_not_newer_than` refuses newer); the engine never reads `data`. `encode_save` / `decode_save` are pure and tested, every damaged-document case has a message that says what is wrong and to run `save.delete <module>`. Modules use `SaveStore::{save, load, delete, modules}` (a Bevy resource) and build values with the re-exported `serde_json` (so they need no serde dependency of their own). **Backends** (`SaveBackend` trait in the contract; `MemorySaveBackend` in the contract): files `saves/<module>.json` natively (`FileSaveBackend` in `platform/native.rs`, temp file then rename, so a crash leaves no half document) and `localStorage` `retreat.save.<module>` in the browser (`platform/wasm.rs`; an unavailable `localStorage` is an error, never a panic). **Under a command script the store is in memory** so a run starts empty and leaves nothing behind; `save.use_platform_backend` opts a script in to the real backend. Commands: `save.write <module> <version> <json>` (JSON without spaces), `save.read|delete <module>`, `save.list`, `save.status`, `save.use_platform_backend`, `assert.save_version|save_field|save_absent`. Saving is local convenience: server authority is unchanged and the platform trusts nothing in a save. Limits: one document per module (no per-key API), no encryption or cloud sync, no multi-slot saves yet; persistence across a browser reload is by `localStorage` and not exercised by a single script run. Checked by `scripts/verify/storage.cmds` (passes natively with files and in the browser with `localStorage`) and the file backend's tests.
- **UI toolkit** (`retreat_engine_api/src/ui_panel.rs`, `retreat_engine/src/ui_panels.rs`; `bevy_ui` as decided earlier): a module declares a panel with `AppUiExt::register_panel(UiPanel { id, title, anchor: TopLeft|TopRight|Center, direction: Row|Column, entries: &[UiButtonEntry { id, label, command_line }], visible })`. The engine draws it and a click (or `ui.press`) runs the entry's command line through `dispatch_command_line`, the one entry point for UI/keys. **Layout is the pure function `compute_panel_layout(entries, has_title, anchor, direction, viewport)`** (constants `PANEL_MARGIN` 12, `PANEL_GAP` 8, `BUTTON_HEIGHT` 36, `ROW_MAX_BUTTON_WIDTH` 150, `COLUMN_BUTTON_WIDTH` 220, `TITLE_HEIGHT` 28): rows share the width equally and shrink in a narrow view; columns shrink their button height (down to `MIN_BUTTON_HEIGHT`) in a short view; positions come only from the visible entries, so hiding a button re-flows the rest; an empty panel lays out to nothing. `UiPanels` (resource) holds each panel, whether it is shown and its hidden entries; `ui_panels.rs` rebuilds all panel UI when the resource changes or the view size changes (`rebuild_panels_when_needed`). The panel root is `Pickable::IGNORE` so it never swallows scene clicks. Commands: `ui.show_panel|hide_panel <panel>`, `ui.hide_entry|show_entry <panel> <entry>`, `ui.press <panel> <entry>` (fires the same `Activate` on the next `Update`; fails with the reason when the button is not shown), `ui.list`. Startup check (`Plugin::finish`): an entry whose command is not registered panics naming `panel/entry` and the command; duplicate panel ids and duplicate entry ids panic. Limits: buttons only (no sliders, text input or scrolling), three anchors, one font size, no keyboard focus order beyond Bevy's. Checked by `scripts/verify/toolbar.cmds` and `module_menu.cmds`.
- **Networking** (`retreat_engine/src/net/`; model decided with the user: server-authoritative with client-side prediction; tests in `tests/engine/net_harness.rs` and `net_webtransport.rs`). **Where the code lives:** the server (`server.rs`, `NetServer` resource, `install_server`) and the client (`client.rs`, `NetClient`, `install_client`) are resources plus systems inside the simulation's own `World`, in `FixedFirst` (read the transport, run due inputs) and `FixedLast` (count the tick, send state, record history), so a real app (Bevy's fixed loop) and the in-process harness (`harness.rs`, `NetHarness`, driven by `simulate_tick(world)`: advance `Time<Fixed>` by one step and run `FixedMain`, same result as a normal update) run the same code. The transport is a non-send resource. **Tick numbers** label the n-th simulated tick on every machine; a client starts `round trip + margin_ticks` ahead of the server (the margin covers jitter plus one tick; negative values make inputs late on purpose); the server counts inputs that arrive after their tick in `late_inputs`. **Inputs are command lines** (everything is a command) queued with `NetClient::queue_input`, run at the start of the next tick and sent as `Input { tick, lines }` (no client id field: the server uses the connection); the server runs only commands in its allow-list and records refusals in `rejected_lines`. **Join:** `Hello { nonce }` (repeated every 16 ticks) answered by `Welcome { nonce, client_id, tick }`; input from a connection that never said hello is ignored. **State:** `body_state.rs` reads and applies `BodyState` (name, `PhysicsBody` description, pose, velocities, sleeping) through Rapier's body set, the only place net code touches it. **Prediction:** the client keeps per-tick history (physics snapshot incl. `SimulationRng` and the fixed clock, body states, inputs); `process_client_states` (before the fixed loop each frame; the harness calls it before each tick; it must run outside `FixedMain` because a replay runs `FixedMain`) compares each server state with the client's own state at that tick (`POSITION_TOLERANCE` 1e-3, `VELOCITY_TOLERANCE` 1e-2); on a mismatch it restores that tick, applies the server states, creates cuboid bodies it lacked (server pose, zero velocity until the next correction), removes bodies the server lacks, and replays its inputs up to its present (`ClientStats`). **Wire format (postcard, decided with the user):** `wire.rs` = one version byte (`WIRE_VERSION`, currently 3, bump with any message-type change) plus postcard; damaged, truncated, empty or other-version bytes give a `WireError`, never a panic; `serde` and `postcard` (alloc only) are workspace dependencies, Bevy's `serialize` feature is on for `Vec3`/`Quat`. **Transport:** `transport.rs` has the non-blocking datagram traits `ServerTransport` / `ClientTransport` and `LoopbackNetwork` (in-process, over `SimulatedLink`s: latency, jitter and loss in ticks, seeded `RetreatRng`). **Native WebTransport** (`platform/native_transport.rs`; `wtransport` 0.7 with Tokio, native-only dependencies, chosen by me because it implements exactly the approved WebTransport with built-in self-signed certificates and hash pinning; the alternative was `quinn` + `h3` with our own session code): `WebTransportServer::start(port)` (0 = free port) makes a self-signed certificate valid 14 days and exposes its SHA-256 (`certificate_hash_hex`); `WebTransportClient::connect(url, Some(hash))` accepts exactly that certificate (W3C `serverCertificateHashes`, no certificate authority needed for testing; `None` uses system roots); both own a small Tokio runtime and use channels so `poll`/`send` never block; a datagram larger than the connection allows (about 1200 bytes) is dropped and counted in `oversized_dropped`. **State size:** only dynamic bodies are replicated (`read_replicated_body_states`: fixed bodies never move and every machine has them from its own scene), a state is cut into chunks of at most `MAX_BODIES_PER_STATE_MESSAGE` (8) bodies (`State { tick, chunk, chunks, bodies }`; a full chunk of long-named bodies is tested to fit 1200 bytes; bodies with names longer than about 40 characters could still overflow and are then dropped and counted), and the client uses a tick only when every chunk arrived (`partial_states`, dropped after 64 newer ticks); a world with 60 boxes replicates to two clients in the harness test. **Verified:** perfect links and links with enough margin give zero corrections; late, lost, jittery and multi-client cases converge after bodies rest; identical setups give identical outcomes; the handshake survives 70% loss; two real WebTransport clients converge with a real server (about 2 s, run repeatedly). Measured: about 7.9 KB/s server to each client (every state lists every body incl. fixed ones) and 0.4 KB/s client to server with 2 clients and 3 bodies. New command `physics.push <name> <vx> <vy> <vz>` is the harness's player action. **Networked apps (native):** `--server <port>` (0 = free port; prints `retreat-net: listening on UDP port <p> certificate-hash <hex>`) and `--connect <https://host:port> [--cert-hash <hex>]` (`NetLaunch` in `LaunchOptions`, installed by `platform::native_transport::install_net` after the game's plugins; the server's allow-list is the game's `NetAllowedCommands` resource, which the sandbox sets to `physics.spawn_box` and `physics.push`); `--real-time` makes a command script run one line per fixed tick of real time (`RealTimeScript`), which a networked process needs because other machines must keep up. Commands: `net.send <command line...>` (the player's input, via `CommandArgs::rest`), `net.status`, `net.bodies` (logs `net-body <name> <x> <y> <z>`), `assert.net_joined`, `assert.net_clients <n>`. **Checked by `scripts/verify/network/run.mjs`** (after `cargo build -p retreat_sandbox`; run in CI): one server and two clients as three real sandbox processes over real WebTransport on localhost, each running a script in real time; it requires every process to exit 0 and the three worlds to agree on every body within 0.05 (3 of 3 runs passed locally). **Browser client:** the page URL takes `?connect=<https://host:port>&cert_hash=<hex>&real_time=1` (a server cannot run in a browser); `web/index.html` defines `window.__retreatNet` (`connect`, `send`, `poll`) on the browser's own `WebTransport` with `serverCertificateHashes`, and `platform/wasm_transport.rs` is the Rust half (events cross as byte arrays: first byte 0 connected, 1 datagram, 2 disconnected). `run_in_browser.mjs` takes `--query <extra URL query>` and prints the page's `net-body` lines. `run.mjs --browser` replaces client B with the browser build (run `scripts/web/build.sh` first): server (native), client A (native) and client B (headless Chrome) agree on every body (passed; CI's browser job runs it). **What a module sees (contract `retreat_engine_api/src/net.rs`):** `NetCommandSender` (who ran the running command: the server sets `Some(client id)` around every command a client sent, a client sets its own id around the commands it predicts, `None` otherwise), the messages `NetClientJoined` / `NetClientLeft` (written by the server), `NetAllowedCommands` (the server runs only these ids; modules add theirs with `AppNetExt::allow_client_command`, the sandbox allows `physics.spawn_box` and `physics.push`), and `NetInputQueue` (a client module pushes command lines here; the engine runs them on the client and sends them, once per tick, never during a replay). `add_net_contract(app)` registers all of it (the engine's `NetCommandsPlugin` calls it; a module's tests call it). `PhysicsVelocityChange(Vec3)` (contract, `physics_body.rs`) asks the engine to add a velocity to a dynamic body once: it waits until the body exists, is applied before the physics step by `apply_velocity_changes`, then removed. `LoopbackNetwork::disconnect` / `NetHarness::disconnect_client` end a connection so a server hears `Disconnected`. **Next:** delta or interest-filtered state to cut bandwidth (every state still lists every moving body), then use the networking in a game module.
- **Physics: Rapier** (`bevy_rapier3d` 0.37, the release for Bevy 0.20; Avian is the fallback). Pinned once in `[workspace.dependencies]` with default features off (no debug render, picking or async colliders) and `enhanced-determinism` on. `PhysicsPlugin` (`physics.rs`) runs Rapier in `FixedUpdate` with `TimestepMode::Fixed { dt: Time<Fixed>::timestep, substeps: 1 }` (the fixed timestep is the one source of truth for tick length), ordered after the script line of the tick (`CommandScriptSystems` before `PhysicsSet::SyncBackend`), so a body spawned by a line simulates in that tick. Commands: `physics.spawn_box <name> <x> <y> <z> <size>` (dynamic cube, marked `PhysicsBox`) and `physics.reset` (removes every `PhysicsBox`). The sandbox ground (a slab collider under the plane) and cube are fixed `PhysicsBody`s.
- **Physics bodies are engine-owned (decided with the user).** Game and module code never puts Rapier's `RigidBody` / `Collider` on its entities; it adds `retreat_engine_api::PhysicsBody { kind, shape, shape_offset }` (the entity needs a unique `Name` and no parent). The description lives in the contract crate and names no physics library (`PhysicsBodyKind::{Dynamic, Fixed}`, `PhysicsShape::{Cuboid, Ball}`), so modules can create bodies without depending on Rapier or on engine internals; `physics.rs::rapier_components` is the one place that maps it onto Rapier (a non-zero `shape_offset` becomes a compound collider). Each tick, `create_physics_proxies` makes one proxy entity per newly added `PhysicsBody`, **sorted by name**, all with the same components (`Name` `<name>/physics`, `PhysicsProxyOf`, `RigidBody`, `Collider`, `Transform`); after `PhysicsSet::Writeback` the proxy's pose is copied to the game entity. Despawning the game entity despawns its proxy (`linked_spawn` relationship). Direct `RigidBody`/`Collider`, an unnamed `PhysicsBody` or one with a parent fails the script with an error. Why: Rapier numbers bodies in the order bevy_rapier's queries visit them, which is Bevy's storage order (each entity's component set and the world's history). Bodies added in the same tick were numbered differently on Windows and Linux (and between scripts), contacts resolved in a different order, and `state.hash` differed in CI. Rejected alternative: a "same components on every body" rule, fragile because any plugin adding a component breaks it silently. Limits today: a `PhysicsBody` is read once (later edits are ignored), and moving the game entity's `Transform` does not move the body. Revisit if bevy_rapier gains a deterministic insertion order.
- **State hash** (`state.hash`, `assert.state_hash <0x…>`, `state_hash.rs`): FNV-1a 64 over every rigid body's (that is, every proxy's) `Name` and the exact bits of its translation and rotation, in name order. FNV is written out because `DefaultHasher` may change between Rust versions. Every rigid body must be named. `scripts/verify/physics_boxes.cmds` asserts a hash recorded on Windows; CI checks it on Linux, which proves cross-platform determinism (browser check comes with the bridge). If physics or the script changes on purpose, put any value in the assert, rerun the script and copy the actual value from the assert's own failure message (`state hash is 0x…`), then say why in the commit. Do not copy the `state.hash = …` print from the line before: it is one tick earlier, which differs whenever a body is still moving (found with `module_spawner.cmds`).
- **UI: `bevy_ui`, Bevy 0.20 widgets.** Buttons are `bevy::ui_widgets::Button` (+ `Hovered`); a completed click fires `Activate` on the button, and an observer runs the button's command line through `retreat_engine::dispatch_command_line(world, source, line)`, the one entry point for UI/keys: it calls `run_command_line`, logs failures and fails a running script. Never call feature logic from UI code, and never run a command inside another command's handler (the registry is taken out of the world while a handler runs; a nested call panics), so UI that is triggered from a command defers to the next system. `Interaction` and the old `bevy_ui::Button` are deprecated in 0.20; do not use them.
- **Sandbox toolbar** (`sandbox/src/toolbar.rs`): a `UiPanel` named `toolbar` (row, top left, visible) declared with the UI toolkit below; the old toolbar-only layout code and `toolbar.*` commands are gone (one source of truth). `SANDBOX_TOOLBAR_ENTRIES` lists the buttons; `sandbox.drop_box` drops a box named `box_<n>` at a `SimulationRng` position and size (engine `spawn_physics_box`). Drive it with `ui.press toolbar <id>`, `ui.hide_entry toolbar <id>`, `ui.show_entry toolbar <id>`. Checked by `scripts/verify/toolbar.cmds`; its four PNGs are byte-identical to those of the old implementation (measured with md5 before and after the migration).
- **Headless UI:** bevy_ui draws on its default camera, chosen among cameras that render to the primary window; headless has none, so `headless.rs` marks the redirected camera Bevy would have chosen (highest `order`, ties by `Entity` ordering) `IsDefaultUiCamera`, unless the game marked one itself. Every snapshot now includes the toolbar.
- **Models: glTF** through Bevy's `AssetServer`. **Shaders: WGSL syntax in `.wesl` files**, within WebGL2 limits.

## Layout

- `crates/retreat_engine_api/` — contract crate (public API for modules): command registry and parsing, `SimulationRng`.
- `crates/retreat_engine/` — engine runtime: `RetreatEnginePlugin` (Bevy `DefaultPlugins` + `RetreatCommandsPlugin`), `LaunchOptions` (`--commands`, `--seed`, `--headless`, `--software-renderer`), the command-script runner, `PendingCommandWork`, `model.spawn` (`model.rs`), material commands and hot-reload fix (`material.rs`), `shader.apply` and the shader material registry (`shader_material.rs`), Rapier, engine-owned bodies and physics commands (`physics.rs`), `dispatch_command_line` for UI/input (`command_dispatch.rs`), `state.hash` (`state_hash.rs`), shader compile errors to script failures (`gpu_pipeline_errors.rs`), asset path rule (`asset_paths.rs`), name lookups (`entity_names.rs`), built-in commands (`wait`, `quit`, `assert.entity_exists`, `assert.position`), `snapshot` (`snapshot.rs`), headless rendering (`headless.rs`), the platform layer (`platform/`), the browser status JSON (`bridge_status.rs`). `RetreatCommandsPlugin` works without a window, so tests add it next to `MinimalPlugins`.
- `crates/retreat_engine/tests/assets/` — files the integration tests load (their `AssetPlugin::file_path`).
- `scripts/verify/*.cmds` — one command script per check; `scripts/verify/*.sh` for checks that must act outside the app during a run (hot reload), with their `.cmds` in a subfolder so the CI loop does not run them alone. CI runs every one with `--headless --software-renderer` and uploads `target/snapshots/` as the `snapshots` artifact. `commands_smoke.cmds` also runs as a sandbox unit test. Run them locally headless first (fastest loop) and open every PNG they write.
- `web/index.html` — the browser page (canvas + `window.__retreat`); `scripts/web/` — `build.sh` (browser build into `target/web/`) and `run_in_browser.mjs` (runs a script in headless Chrome).
- `sandbox/` — crate `retreat_sandbox`, the Engine Sandbox app that exercises every engine feature. `sandbox/assets/` is its asset folder (`models/`, `textures/`, `shaders/`), credited in `sandbox/assets/CREDITS.md`.

## Architecture rules

- Dependency direction: `Retreat-CoreSDK` → contract crates → engine and modules → generated game. Never reverse it.
- **Shared generic helpers:** check `Retreat-CoreSDK` first. A helper stays in the engine until a second consumer (a module) needs it; then move it to CoreSDK instead of copying it. What belongs in CoreSDK, and what does not, is defined in `../Retreat-CoreSDK/CLAUDE.md`. Shared gameplay concepts go in the engine's public API / contract crates, not in CoreSDK.
- Modules depend on contract crates (traits, events, component types), never on each other and never on engine internals.
- Expose a small, stable, documented public API. Keep renderer and networking internals private.
- Isolate all `cfg(target_arch = "wasm32")` code in a single platform layer. Do not assume native capabilities (threads, filesystem, sockets) exist in the browser; assume single-threaded WASM as the baseline.
- Configuration must be reproducible: the same module selection must rebuild the same project.
- Generated project structures must be predictable and documented so humans and AI agents can customize them safely.
- Distinguish trusted first-party modules from untrusted third-party or AI-generated code. Rust memory safety is not sandboxing.

## Working rules

- Keep the initial implementation as simple as reasonably possible.
- Do not modify sibling repositories from this one without being asked.
- Write documentation and code comments in English.

## Verification

Applies once the engine has a first loop; build the missing pieces in this order when a task needs them.

1. **Command registry** (`snapshot <png>`, `wait <frames>`, `quit`, `assert.*`). Input and UI dispatch through it. Scripts run one line per frame, fixed timestep, seeded RNG.
2. **Headless snapshot:** `cargo run --example <x> -- --headless --commands <file>` renders to an offscreen wgpu texture and writes a PNG. Open it. CI uses a software adapter (lavapipe/WARP).
3. **Browser bridge:** serve the WASM build (`trunk serve` or wasm-bindgen) and expose `window.__retreat.command()` / `snapshot()`. Run the same scripts to check WASM-only behavior. `wasm-bindgen-test` (headless Chrome) covers WASM-only logic in CI.
4. **Per change:** `cargo check` for native and `wasm32-unknown-unknown`, plus `cargo nextest`.
5. **Determinism:** the same script must give the same state hash on native and WASM. Mismatch means platform drift.
6. **Netcode:** test server plus N fake clients in one process with simulated latency, not in browsers.
7. **Performance:** frame time and draw-call count are readable via commands so budgets can be asserted.
